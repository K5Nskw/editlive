# EditLive

RTMP で受け取ったライブ映像を **そのままブラウザで編集して、書き出し・配信する** ところまでを 1 つのサービスにまとめたものです。WSC Sports のワークフロー（ライブ取り込み → クリップ生成 → 各配信先へ展開）を参考にしています。

```
OBS / エンコーダー
      │ RTMP push
      ▼
┌──────────────────────────────────────────────────────────────┐
│ EditLive (Node.js + ffmpeg)                                  │
│                                                              │
│  RTMP 取り込み ──► 録画  ─┬─► HLS (配信中もシークできる)      │
│  (node-media-server)      └─► MP4 (編集・書き出しの原本)      │
│         │                                                    │
│         ▼ 配信終了                                            │
│  後処理: faststart MP4 / ポスター / タイムライン用サムネイル   │
│         │                                                    │
│         ▼                                                    │
│  解析: 音量(RMS) + 動きの大きさ + カット検出                  │
│         └─► タイムラインに重ねる波形とカット位置              │
│         │                                                    │
│         ▼                                                    │
│  ブラウザ編集: イン/アウト・縦横比・ぼかし背景・テロップ       │
│         │                                                    │
│         ▼                                                    │
│  書き出し: MP4 保存 + ダウンロード / 公開リンク                │
│            YouTube アップロード / Buffer 投稿 / Webhook       │
└──────────────────────────────────────────────────────────────┘
```

## できること

- **RTMP 取り込み** — ストリームキーごとに入力を分けられます。接続を検知すると自動で録画を開始します。
- **配信中から編集可能** — 録画は HLS のイベントプレイリストとして書き続けるので、配信が続いている最中でも先頭から巻き戻して編集できます。
- **切りどころが見えるタイムライン** — 音量・画面の動き・カット割りを 1 秒刻みで測り、フィルムストリップに重ねて描きます。どこで盛り上がっているかを目で追いながら範囲を決められます（区間の自動提案は行いません）。
- **ブラウザ編集** — タイムライン上でイン点／アウト点をドラッグして決めます。キーボードショートカット（Space / I / O / ←→）にも対応。
- **縦型書き出し** — 9:16 / 1:1 / 4:5 / 16:9。はみ出す部分は「ぼかし背景に収める」か「切り抜いて埋める」（位置調整つき）を選べます。日本語テロップ、フェード、ミュートに対応。
- **書き出し先** — サーバー内保存＋ダウンロード、ログイン不要の公開リンク、YouTube への直接アップロード、Buffer 経由の SNS 投稿、任意の Webhook。

## ローカルで動かす

必要なもの: Node.js 22 以上、ffmpeg / ffprobe（PATH 上）。

```bash
npm install
npm run dev          # API+RTMP を :3000 / :1935、Vite を :5173 で起動
```

ブラウザで http://localhost:5173 を開きます。`APP_PASSWORD` を設定していない場合は、起動ログに一時パスワードが出ます。

```
WARN  [main] APP_PASSWORD is not set — this run's login password is "xxxxxxxx"
```

本番と同じ構成（ビルド済み SPA を Express が配る）で動かす場合:

```bash
npm run build
APP_PASSWORD=your-password npm start   # http://localhost:3000
```

テストと型チェック:

```bash
npm test         # 波形の正規化とレンダリング寸法のユニットテスト
npm run typecheck
```

### OBS の設定

| 項目 | 値 |
| --- | --- |
| サービス | カスタム |
| サーバー | 画面に表示される `rtmp://<ホスト>:<ポート>/live` |
| ストリームキー | 画面に表示されるキー |

映像は **H.264**、音声は **AAC** で送ってください（OBS の既定値どおり）。録画はコーデックを変換せずそのまま保存するため、他のコーデックだと取り込みに失敗します。

## Railway へのデプロイ

1. **サービスを作る** — このリポジトリを Railway に繋ぎます。`railway.json` があるので `Dockerfile` でビルドされます。
2. **ボリュームを追加する** — 録画とクリップはディスクに置かれます。マウント先を `/data` にしてください（`DATA_DIR` の既定値）。ボリュームが無いと再デプロイのたびに録画が消えます。
3. **HTTP ドメインを有効にする** — Settings → Networking → Public Networking で、ターゲットポートに `PORT`（Railway が渡す値）を割り当てます。
4. **RTMP 用に TCP Proxy を足す** — 同じ Networking 画面で **TCP Proxy** を追加し、コンテナ側ポートに **1935** を指定します。発行された `<host>:<port>` がエンコーダーの接続先になります。Railway は `RAILWAY_TCP_PROXY_DOMAIN` / `RAILWAY_TCP_PROXY_PORT` を環境変数として渡すので、アプリはそれを読んで画面に表示します。手動で上書きしたい場合は `RTMP_PUBLIC_HOST` / `RTMP_PUBLIC_PORT` を設定してください。
5. **環境変数を設定する** — 最低限 `APP_PASSWORD` だけ設定すれば動きます。詳細は `.env.example` を参照。

> **注意**: HTTP ドメインは HTTPS を終端しますが、RTMP は TCP Proxy を素通りする平文です。ストリームキーが漏れないよう、キーは共有範囲を絞り、疑わしいときは画面から再発行してください。

### リソースの目安

書き出しは ffmpeg の再エンコードなので CPU を使います。既定では同時実行数 1（`JOB_CONCURRENCY`）で、クリップは順番に処理されます。長時間の配信を扱う場合はメモリよりも **ディスク容量** が先に問題になります（1080p / 6 Mbps で 1 時間あたり約 2.7 GB）。`MAX_RECORDING_HOURS` が 1 本あたりの上限です。

## タイムラインの波形について

1. 録画が終わると、ffmpeg で 2 パス解析します。
   - 音声: `asetnsamples` で 1 秒ごとに切り、`astats` の RMS レベル（dBFS）を取得。
   - 映像: 320px・5fps に落として全フレームのシーンスコアを取得。1 秒ごとの平均が「動きの大きさ」、0.35 を超えた瞬間が「カット」。
2. どちらもその録画自身の中央値を基準（ベースライン）にして 0〜1 に正規化し、`0.72 × 音量 + 0.28 × 動き` を 1 本の曲線にまとめます。音声が無い録画では動きだけを使います。
3. その曲線とカット位置をタイムラインに重ねて描きます。

絶対的な音量しきい値ではなく素材の中での相対値を見るので、静かなスタジオ配信でも歓声だらけのスタジアムでも同じ見え方になります。**どこを切るかの判断は行いません** — 目印を出すだけで、範囲は人が決めます。

## 書き出し先の設定

### サーバー保存とダウンロード

設定不要です。書き出したクリップは `DATA_DIR/clips` に MP4 (H.264/AAC, faststart) で保存され、編集画面からダウンロードできます。クリップごとに推測不能なトークン付きの公開リンク（`/p/<token>.mp4`）も発行され、これはログインなしで再生できます。リンクを無効にしたいときはクリップを削除してください。

### YouTube

1. Google Cloud Console でプロジェクトを作り、**YouTube Data API v3** を有効にします。
2. OAuth クライアント（ウェブアプリケーション）を作り、リダイレクト URI に次を登録します。
   `https://<あなたのドメイン>/api/integrations/youtube/callback`
   （設定画面にそのままコピーできる形で表示されます）
3. `GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET` を Railway の環境変数に設定します。
4. 設定画面から「Google アカウントを接続」を押します。リフレッシュトークンは `DATA_DIR` の SQLite に保存され、再起動しても接続は維持されます。

未審査の OAuth クライアントでアップロードした動画は、YouTube 側の制限で公開範囲が強制的に「非公開」になります。公開したい場合は Google の審査を通してください。

### Buffer

Buffer の開発者ページで発行したアクセストークンを設定画面に登録すると、接続済みプロフィール（X / Facebook / LinkedIn など）が一覧に出ます。

Buffer の公開 API は動画ファイルの直接アップロードに対応していないため、**クリップの公開リンクを添付した投稿**として送信されます。動画そのものを各 SNS のネイティブ動画として上げたい場合は、ダウンロードして各サービスに投稿するか、YouTube 連携を使ってください。

### Webhook

送信先 URL を登録すると、クリップを書き出したあとに次の JSON が POST されます。

```json
{
  "clipId": "clip_...",
  "title": "決勝ゴール",
  "durationSeconds": 18.5,
  "bytes": 5242880,
  "mediaUrl": "https://<ドメイン>/p/<token>.mp4",
  "thumbnailUrl": "https://<ドメイン>/p/<token>.jpg",
  "recordingId": "rec_...",
  "publishedAt": "2026-09-15T06:47:38.268Z"
}
```

シークレットを設定した場合は `x-editlive-signature: sha256=<HMAC-SHA256(body)>` が付きます。Zapier や自前のバッチから繋ぐときに使ってください。

## 構成

```
server/            Express API + RTMP 取り込み + ffmpeg パイプライン
  src/ingest/      RTMP サーバーと録画プロセスの管理
  src/media/       ffmpeg ラッパー・解析・クリップレンダリング
  src/jobs/        SQLite に永続化した直列ジョブキュー
  src/publish/     YouTube / Buffer / Webhook
  src/routes/      REST API
web/               React + Vite の編集 UI（ビルド結果は server/public へ）
```

- **状態は SQLite 1 ファイル**（`DATA_DIR/editlive.db`）。外部データベースは不要です。
- **ジョブは永続化**されるので、書き出し中に再起動しても起動時に再実行されます。配信中に落ちた録画も、次の起動時に後処理へ回されます。
- **認証はパスワード 1 つ**の単純な仕組みです。署名付き Cookie でセッションを保持します。複数ユーザーや権限管理は入っていません。

## 主な API

すべて Cookie 認証（`/p/*` の公開リンクを除く）。

| メソッド | パス | 説明 |
| --- | --- | --- |
| `GET` | `/api/streams` | 入力一覧（RTMP URL とキーを含む） |
| `POST` | `/api/streams/:id/rotate-key` | ストリームキーの再発行 |
| `GET` | `/api/recordings` | 録画一覧 |
| `GET` | `/api/recordings/:id` | 録画 + クリップ |
| `GET` | `/api/recordings/:id/analysis` | タイムライン用の波形・カット位置 |
| `POST` | `/api/recordings/:id/analyze` | 波形を作り直す |
| `POST` | `/api/clips` | 範囲と見た目を指定してクリップを作成 |
| `GET` | `/api/clips/:id/download` | MP4 のダウンロード |
| `POST` | `/api/clips/:id/publish` | `youtube` / `buffer` / `webhook` へ送る |
| `GET` | `/healthz` | ヘルスチェック |

## 制限と注意点

- 取り込みは **H.264 + AAC の RTMP** のみです。録画はコーデック変換せずそのまま保存します（CPU を使わず、画質も落ちません）。
- エンコーダーが切断してから **約 30 秒** は再接続を待ちます（node-media-server の猶予時間）。この間は録画が続き、猶予が過ぎてから後処理と解析が始まります。
- 解析は録画全体をデコードします。映像は 320px / 5fps に落としているため実時間よりは速いものの、長時間の録画では数分かかります。
- タイムラインの波形は音と動きだけを見ています。スコアボードや実況テキストの認識は行いません。
- 同時に扱えるのは 1 プロセス・1 コンテナ分です。水平スケールする設計にはなっていません（ディスクとジョブキューがローカル前提）。
